# gRPC Performance & Observability Lab

Инструмент для **нагрузочного тестирования, измерения производительности и анализа работы gRPC-сервисов на Go**.

Проект помогает не просто отправить несколько RPC-запросов, а получить данные, по которым можно понять, **как сервис ведёт себя под нагрузкой, где возникают задержки и ошибки и что происходит с отдельными запросами внутри системы**.

## 🎯 Что можно получить от проекта

С помощью проекта можно:

* проверить, как gRPC-сервис работает при разной интенсивности нагрузки;
* измерить **latency** и посмотреть распределение задержек на уровнях **p50, p90 и p99**;
* сравнить поведение сервиса при лёгкой, постоянной и пиковой нагрузке;
* проверить производительность разных типов gRPC-взаимодействия;
* измерить количество успешных и ошибочных RPC-запросов;
* анализировать TPS и размеры запросов и ответов;
* наблюдать собранные метрики через **Prometheus**;
* исследовать путь отдельного RPC-запроса с помощью **OpenTelemetry и Jaeger**;
* использовать подробное логирование для поиска проблем во время тестирования;
* тестировать gRPC-сервисы с TLS/mTLS;
* воспроизводить одинаковые сценарии нагрузки с заданным количеством запросов и параллельных горутин.

Таким образом, репозиторий можно использовать как **готовую лабораторную среду для экспериментов с производительностью gRPC** или как основу для собственных нагрузочных тестов.

## 🚀 Для каких задач подходит

Проект будет полезен, если нужно:

### Проверить производительность gRPC-сервиса

Можно задать количество запросов и уровень параллелизма, после чего посмотреть, как изменяется время обработки RPC и поведение сервиса под нагрузкой.

### Найти проблемы с latency

Распределение latency по **p50, p90 и p99** позволяет увидеть не только среднее время ответа, но и поведение более медленных запросов.

### Проверить разные модели нагрузки

Клиент поддерживает три сценария:

* `light` — небольшая нагрузка с паузами между запросами;
* `peak` — приближенная к пиковой нагрузка с короткими случайными паузами;
* `constant` — постоянная нагрузка без пауз.

Это позволяет воспроизводить разные условия работы сервиса и сравнивать результаты.

### Исследовать разные типы gRPC RPC

В проекте реализованы четыре варианта взаимодействия:

| Метод               | Тип RPC                 | Что позволяет проверить                          |
| ------------------- | ----------------------- | ------------------------------------------------ |
| `Ping`              | Unary                   | Базовую latency и успешность отдельных RPC       |
| `Stats`             | Unary                   | Получение статистики работы сервера              |
| `PushNotifications` | Server Streaming        | Передачу множества сообщений от сервера          |
| `AggregatePing`     | Client Streaming        | Передачу серии сообщений от клиента              |
| `StreamPing`        | Bidirectional Streaming | Двунаправленный обмен данными в реальном времени |

Это позволяет сравнивать поведение Unary, Server Streaming, Client Streaming и Bidirectional Streaming сценариев.

## 📊 Нагрузочное тестирование

Клиент позволяет управлять основными параметрами нагрузки:

* `requests` — количество запросов или сообщений;
* `concurrency` — количество параллельных горутин;
* `scenario` — сценарий нагрузки.

Например:

```go
requests := 1000
concurrency := 50
scenario := client.ScenarioPeak

client.UnaryPing(c, requests, concurrency, scenario)
client.StreamPing(c, 100, concurrency, scenario)
client.PushNotifications(c, "start", concurrency, scenario)
client.AggregatePing(c, 50, concurrency, scenario)
```

Это позволяет воспроизводить одинаковые условия тестирования и сравнивать результаты разных запусков.

## 📈 Prometheus: метрики производительности

Сервер интегрирован с Prometheus и собирает метрики gRPC-вызовов.

Доступны:

| Метрика                        | Тип       | Что показывает                       |
| ------------------------------ | --------- | ------------------------------------ |
| `grpc_rpc_requests_total`      | Counter   | Количество RPC-запросов и их статус  |
| `grpc_rpc_latency_seconds`     | Histogram | Распределение времени выполнения RPC |
| `grpc_rpc_request_size_bytes`  | Histogram | Размер входящих запросов             |
| `grpc_rpc_response_size_bytes` | Histogram | Размер ответов                       |

Метрики содержат информацию о конкретных gRPC-методах и статусах запросов.

Endpoint метрик:

```text
http://localhost:9090/metrics
```

Полученные данные можно использовать непосредственно в Prometheus или визуализировать через Grafana.

## 🔎 OpenTelemetry + Jaeger

Prometheus помогает увидеть **числовые показатели**, а OpenTelemetry и Jaeger позволяют исследовать **отдельные запросы и их трассы**.

Для каждого RPC создаётся span с информацией о:

* вызываемом методе;
* статусе;
* времени выполнения.

Используется Jaeger Collector:

```text
http://localhost:14268/api/traces
```

Jaeger UI:

```text
http://localhost:16686
```

Это позволяет перейти от вопроса:

> «Почему выросла latency?»

к более детальному анализу:

> «Какой именно RPC выполнялся долго и сколько времени занял его span?»

## 🔐 TLS / mTLS

Проект содержит сценарий настройки TLS/mTLS для клиентского и серверного взаимодействия.

Можно создать собственный CA и сертификаты для:

* сервера;
* клиента.

Это позволяет использовать проект не только для тестирования производительности обычного gRPC-соединения, но и для экспериментов с защищённым взаимодействием.

### Создание CA

Перейдите в:

```text
cmd/server/certs
```

Создайте приватный ключ:

```bash
openssl genrsa -out ca.key 4096
```

Создайте сертификат CA:

```bash
openssl req -x509 -new -nodes \
  -key ca.key \
  -sha256 \
  -days 3650 \
  -subj "/CN=Test-CA" \
  -out ca.crt
```

Полученные `ca.crt` и `ca.key` используются при настройке клиентских и серверных сертификатов.

## 🪵 Логирование

Логи сохраняются в отдельную директорию:

```text
logs/
```

Основные файлы:

```text
server.log
client.log
```

В них можно найти информацию о:

* выполненных RPC;
* времени запросов;
* статусах;
* ошибках;
* отладочных сообщениях.

Для дополнительного вывода используются флаги:

```text
-debug
-verbose
```

### Сервер

```bash
go run cmd/server/main.go -debug
```

### Клиент

```bash
go run cmd/client/main.go -verbose
```

## 🛠 Запуск проекта

### 1. Сгенерировать Go-код из `.proto`

```bash
protoc \
  --go_out=. --go_opt=paths=source_relative \
  --go-grpc_out=. --go-grpc_opt=paths=source_relative \
  proto/benchmark.proto
```

### 2. Запустить сервер

```bash
go run cmd/server/main.go
```

### 3. Запустить клиент

```bash
go run cmd/client/main.go
```

После запуска можно использовать клиент для выполнения нагрузочных тестов и наблюдать за результатами через Prometheus и Jaeger.

## 🐞 Отладка в VS Code

Проект содержит конфигурации для запуска и отладки клиента и сервера из Visual Studio Code.

Доступны сценарии:

* **Debug Server** — запуск gRPC-сервера с отладочными параметрами;
* **Debug Client** — запуск клиента;
* **Debug Server + Client** — одновременный запуск клиента и сервера.

При необходимости можно использовать:

```text
-debug
```

для отладочных сообщений и:

```text
-verbose
```

для подробного вывода работы клиента.

При этом сами флаги не являются обязательными для работы отладчика VS Code.

## 💡 Что можно исследовать с помощью проекта

Проект можно использовать как практическую площадку для экспериментов:

**Производительность**

Как изменяется latency при увеличении количества параллельных запросов?

**Нагрузка**

Как сервис ведёт себя при `light`, `constant` и `peak` нагрузке?

**RPC-модели**

Чем отличается поведение Unary RPC от streaming-взаимодействия?

**Наблюдаемость**

Какие метрики помогают понять состояние сервиса, а какие детали можно увидеть только в трассировке?

Как изменяется количество успешных и ошибочных RPC при росте нагрузки?

**Диагностика**

Можно ли по метрикам и трассам определить, какие запросы выполняются дольше остальных?

## 🧠 Идея проекта

Это не просто пример gRPC-сервера и клиента.

Проект объединяет **нагрузочное тестирование + метрики + распределённую трассировку + логирование**, чтобы разработчик мог воспроизводить нагрузку и одновременно наблюдать, что происходит с сервисом.

Именно поэтому репозиторий можно использовать как небольшую **лабораторию для изучения производительности и observability gRPC-сервисов на Go**.
